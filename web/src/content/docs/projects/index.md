The best next project is one you would enjoy changing after the basic version works. These guides give you a destination and a path, but they do not provide finished code. You will decide how the program sounds, how its data is organized, and which extra features are worth keeping.

## Three starting points

| Project | What you will make | Good practice for |
| --- | --- | --- |
| [Study planner](./study-planner/) | A task list that can add work, mark it done, and show what remains | Lists, dictionaries, loops, menus, and files |
| [Event budget checker](./event-budget/) | A tool that records expenses and tells you how much of a budget remains | Numbers, validation, functions, and summaries |
| [Question-bank editor](./question-bank-editor/) | A tool for drafting quiz questions and checking their answer data | Nested collections, validation, searching, and reports |

You can rename any project or move it into a setting you care about. A study planner can become an org task board. An event budget can become a personal savings tracker. Keep the first version small before changing the theme.

## Work in versions

Every guide has milestones. Finish one, run it several times, then save a Git commit before beginning the next. A milestone is useful only when the program works at that point. Half of three features is harder to debug than one finished feature.

Start each project in its own folder with a blank Python file. Do not copy your quiz and delete parts until it resembles something new. Starting from zero makes you decide what this program actually needs.

Your first version may have fixed data written in the file. That is fine. Add user input after the basic calculation or display works. Add a menu after one action works. Add file saving after the program behaves correctly in memory.

## Keep a small project note

Before coding, write four short answers in a README or on paper:

1. Who will use this program?
2. What should they be able to do in the first finished version?
3. What information must the program remember while it runs?
4. What result tells you the program worked?

These answers are your first specification. Change them when you learn something, but write down the change. Otherwise the project can quietly grow until nothing feels finished.

## When to ask for help

Ask about one behavior at a time. Show the current output, the output you expected, and the smallest part of the program that reproduces the problem. Someone can guide you without taking over the project.

There is no required final design. If your version completes the core checks on its project page and you can explain its main decisions, it is finished enough to share.
